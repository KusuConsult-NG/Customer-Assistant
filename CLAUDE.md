# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Customer Care Platform — a multi-tenant AI citizen-care platform for a State Government, operated by the Ministry of Information with every ministry, department and agency as an isolated tenant of ONE deployment. Repurposed from a commercial product whose flagship tenant was a health insurance scheme; see `PROVENANCE.md` for what was removed and what is still scheme-specific. **The platform administration tier is the ONE deliberate exception to tenant isolation** — see the section below before touching it. **No subscription billing and no citizen payment collection exist here**; both were removed deliberately, so do not reintroduce a payment path without being asked. **Customers reach it on WhatsApp and by phone; the web app is the staff dashboard.** (The embedded web-chat widget was a third customer channel and has been RETIRED — see below.) Internal identifiers still use the original `ace` prefix on purpose (`@ace/*` package names, the `ace_token` localStorage key, the `ace_live_pk_` key prefix): those are functional, not display strings, and renaming them would invalidate issued keys and stored sessions. npm-workspaces monorepo driven by Turbo: `apps/api` (NestJS 10), `apps/web` (Next.js 15 App Router), and `packages/*` (Prisma database client, conversation orchestrator, provider SDKs).

## Commands

```bash
npm install                        # root install (workspaces)
npx turbo run build                # build everything (api, web, all packages)
npx turbo run build --filter=@ace/api...   # api + its package dependencies
npm run db:generate                # prisma generate (packages/database)
npm run db:push                    # prisma db push — REQUIRED after any schema.prisma change
```

`DATABASE_URL` **and** `DIRECT_URL` must both be set for any Prisma command (pooled + direct connection; point both at the same DB locally).

### Tests

There is no single test runner. Three layers, all proven to run:

```bash
# 1. Package unit suites (plain node scripts; packages must be BUILT first)
cd packages/<name> && node test/run-test.js     # orchestrator needs DATABASE_URL/DIRECT_URL

# 2. API integration tests (Jest + supertest; needs a live PostgreSQL)
cd apps/api && npx jest --forceExit
cd apps/api && npx jest --forceExit -t "retired"          # single test by name

# 3. Browser e2e (Playwright; needs the FULL stack running: API on :4000, web on :3000)
cd apps/web && npx playwright test
```

Local full-stack recipe (no Docker needed if postgres/redis binaries exist):

```bash
cp .env.example .env          # every required var, with the traps annotated
npx turbo run build

# PostgreSQL 16 must run as a non-root user; Redis is optional but enables
# BullMQ ingestion, cross-pod Socket.IO, and Redis-backed rate limiting.
#
# Do NOT export .env into your shell with `set -a; . ./.env; set +a`. That
# executes the file, so a password containing ( ) * ! or a space is a syntax
# error — all legal in a .env, and dotenv reads them fine. Prisma and the API
# both read the file themselves; `scripts/dev-setup.sh` parses it as text.
npx prisma db push --schema=packages/database/prisma/schema.prisma

# `db push` CANNOT create the booking EXCLUDE constraint (Prisma cannot express
# EXCLUDE), so apply it separately or concurrent double-booking stays possible.
# Only the EXCLUDE ones: db push already created everything the other
# migrations describe, so re-running them collides.
for m in $(grep -l 'EXCLUDE USING' packages/database/prisma/migrations/*/migration.sql | sort); do
  psql "$DIRECT_URL" -v ON_ERROR_STOP=1 -f "$m"
done

node apps/api/dist/main.js
cd apps/web && npx next start -p 3000

npm run db:seed:gatekipa      # optional: a demo tenant with FAQs
npm run demo:readiness        # what actually works right now, per capability
npm run verify                # every test layer; missing prerequisites SKIP, never pass
```

Four things that cost real debugging time:

- **`FATAL: sorry, too many clients already` is usually arithmetic, not load.** Jest isolates every test FILE — fresh module registry, fresh `globalThis`, even a fresh `process` shim — so `@ace/database`'s singleton is one client per file, and each one's pool stayed open for the life of the worker. Thirteen files per worker exhausted PostgreSQL's default 100 connections, and it surfaced from whichever suite was running at the peak, which reads exactly like a fault in that suite. `apps/api/test/support/release-db-connections.ts` disconnects when a file ends (a root `afterAll` from `setupFilesAfterEnv` runs AFTER the suite's own, which is the only ordering that works — the suites clean up fixtures through that same client). Measured peak went 97 → 33. Do not "fix" a recurrence by lowering `DATABASE_CONNECTION_LIMIT`: that shrinks each pool, not the number of them, and at 10 the eight-way booking race stops being concurrent, so the test that proves the `EXCLUDE` constraint reports no refusals and reads as "the constraint is gone".

- **Startup validation rejects any value containing "placeholder"**, deliberately. Use a real-looking dummy.
- **Restart `next start` after a rebuild.** It serves the build that existed when it booted; after a rebuild it hands out chunk URLs that 404, React never hydrates, and every browser test fails with "element(s) not found" that reads exactly like a real regression. `scripts/verify-all.sh` detects this and skips rather than reporting a false failure.
- **Never point `DATABASE_URL` at production.** The harness and probes create real organizations through the real API — that is why they catch bugs mocks do not. Pointed at production once, they left 358 test organizations and ~13,900 contacts in the live CRM.

The Playwright suite registers its own org through the real API and injects the JWT into localStorage before each page load — every dashboard page is behind the layout auth guard, so tests cannot simply `goto()` a page. The app shell renders its own `<h1>Customer Care Agent</h1>`, so bare `h1` locators are strict-mode ambiguous; filter by text.

### Claude Code on the web: none of the above has to be done by hand

`.claude/hooks/session-start.sh` runs the whole recipe above at session start — install, `prisma generate`, PostgreSQL 16 + `ace_dev`, `db push`, the EXCLUDE migrations, Redis, `turbo run build` — and exports the resulting `.env` into the session's shell so the package suites find `DATABASE_URL`. A web session therefore begins with `npm run verify` already runnable, instead of spending its first several minutes rebuilding the stack out of this file.

**It is async, so the stack is still being built while the session runs. Gate on it:**

```bash
./.claude/hooks/wait-for-ready.sh && npm run verify
```

The session starts immediately rather than waiting out the build, which means the agent loop races the hook. A suite run before `turbo run build` has written `dist/`, or a query issued before `prisma db push` finishes, fails in exactly the way a real regression does — and that misreading is expensive here, which is what the wait script is for. It blocks until provisioning finishes, prints `ready` or the specific gaps, and exits non-zero only if provisioning actually failed; degraded still exits 0, because everything that did come up is still worth debugging against. Off the web container it is a no-op.

- **It only runs when `CLAUDE_CODE_REMOTE=true`.** A local machine has its own PostgreSQL and its own `.env`, and the hook has no business touching either.
- **It refuses a non-local `DATABASE_URL`** rather than pushing schema into it — same reason as the warning above.
- **It always exits 0**, and reports each layer it could not bring up. A hook that fails the session start leaves no session in which to fix the hook, and a layer silently assumed present produces test failures that read exactly like real regressions.
- **The linter here is the type checker.** There is no ESLint configuration in the repo and `apps/web`'s `next lint` would try to create one interactively; `npm run typecheck` is what actually gates the code.

### Plugins: declared in the repo, because the claude.ai ones do not arrive

The web container sets `SKIP_PLUGIN_MARKETPLACE=true`, so plugins enabled on claude.ai are never delivered to a session — `~/.claude/plugins/synced/` stays empty and none of their skills load. Skills sync is unaffected; only plugins are.

The git marketplace layer is a separate mechanism and still works, so `.claude/settings.json` declares what this repo actually uses, as `extraKnownMarketplaces` + `enabledPlugins`:

| Plugin | Source | Why | Always-on cost |
|---|---|---|---|
| `superpowers` | `obra/superpowers` | 14 skills — `systematic-debugging`, `test-driven-development`, `verification-before-completion` | ~688 tok |

**`twilio-developer-kit` (`twilio/ai`) was tried and deliberately dropped.** Its 57 skills cover SMS, Voice, WhatsApp, webhooks and TwiML — exactly the providers this platform is built on — but they cost **~8.8k tokens on every session, whatever that session is doing**, and the point of this setup was to make sessions cheaper. Twilio specifics are better fetched when a task actually needs them than carried by every session that does not. To put it back:

```bash
claude plugin marketplace add twilio/ai --scope project
claude plugin install twilio-developer-kit@twilio --scope project --yes
```

Two things to know if you do. It ships one MCP server, `twilio-docs` — an HTTP endpoint at `mcp.twilio.com/docs`, documentation search rather than the Twilio REST API, so it cannot touch a tenant's account; it needs an OAuth flow no web session can run, so it stays unauthenticated and its tools are unavailable while the 57 skills work fine. And `claude plugin details` reports `MCP servers (0)` for it, which is wrong — the server is declared in `mcp.json`, not `plugin.json`. Add the marketplace name to the check loop in `.claude/hooks/session-start.sh` so the hook reports it.

Two things worth knowing before changing this:

- **The hook reports plugin state, it does not install it.** Plugin skills load as the session starts, which is while the hook is still running, so anything installed from the hook would first take effect in a session this container will never have. Declaring them in settings is what makes them load; the hook only says whether it worked.
- **Only 3 of the 20 claude.ai plugins have a git source at all** (`superpowers`, `twilio-developer-kit`, `postiz`). The rest — `engineering`, `finance`, `legal`, `data` and the other first-party ones — are delivered only through the claude.ai channel and cannot be bridged this way. They are business/connector workflows rather than coding tools, so this loses nothing here.

## Architecture

**Request flow**: Next.js pages call the API directly via `fetch` (`apps/web/src/lib/api.ts` builds the base URL; JWT from `localStorage.ace_token`). The NestJS API is a modular monolith — one module per domain (auth, organizations, crm, whatsapp, telephony, knowledge, scheduling, workflows, analytics, events, onboarding, agent-tools, webhooks; `widget` is a retirement stub).

**Database access**: a single shared `PrismaClient` exported from `@ace/database` (`import { prisma } from '@ace/database'`) — NOT injected via Nest DI. Services import it directly; so do the orchestrator and worker packages.

**Multi-tenancy** is by `organizationId` scoping on every query — there is no automatic tenant filter. Every service method takes `organizationId` from the JWT (`req.user.organizationId`) and must include it in `where` clauses.

**The platform administration tier (`apps/api/src/platform`) is the ONE place that crosses the agency boundary**, and it is built so that widening it has to be deliberate.

- **Reached only via `/api/platform/*`**, guarded at the CLASS level by `JwtAuthGuard` then `PlatformAdminGuard`. That order is load-bearing: Nest runs guards global → controller → route, so the platform guard alone would execute before authentication and see no user. It refuses in that case rather than allowing — the opposite of how the subscription guard this repo once had failed open.
- **`User.isPlatformAdmin` is deliberately NOT a `UserRole` value.** `PATCH /api/organizations/members/:id/role` writes `UserRole`, so a platform role listed there would be grantable by any agency ADMIN to themselves. As a separate column of a different type the endpoint cannot express it, so the escalation is closed by the schema rather than by a check someone has to remember. A test asserts the role endpoint rejects it.
- **Nothing in the HTTP API grants it.** `npm run platform:grant` sets it at the database (report-first; `--apply` writes; `--revoke --apply` removes), so the set of people who can read across every ministry is bounded by who holds database credentials. There is no bootstrap path in the application: a fresh deployment has no operator until somebody creates one.
- **The flag is read from the DATABASE on every request**, never from the token — `JwtStrategy` selects it. A forged `isPlatformAdmin` claim is inert, and revoking takes effect on the next request. A test mints such a token and asserts 403.
- **METRICS AND CONFIGURATION, NEVER CONTENT.** No method in `PlatformService` returns a message body, transcript, recording, citizen name or citizen phone number. The ministry's job is service standards across agencies, which needs counts; an oversight tier that can read every conversation in the State is a surveillance capability nobody asked for. A test seeds a contact and a message and asserts neither appears in any platform response — that assertion is what stops a future `include:` from quietly creating one.
- **Suspension is real, not a flag.** `Organization.suspendedAt` is checked in `JwtStrategy`, so every member of a suspended agency is refused on their next request. Platform operators are exempt or a suspension could never be lifted, and an operator cannot suspend their own agency. A reason is required and recorded.
- **Every mutating action is audited** to `AuditLog`, awaited and not swallowed — the operator is the one actor whose reach is not bounded by tenant scoping, so "who did this to our agency" must always have an answer. `AuditLog` is append-only, so the tier cannot edit the record of its own actions.
- **The console lives at `/platform`** (`apps/web/src/app/platform/page.tsx`). Its sidebar link is drawn from `isPlatformAdmin` in the stored `ace_user`, which is a CONVENIENCE and not a permission — localStorage is editable, so the page simply calls the API and renders the "unavailable" panel on a 403. An e2e signs in as an agency owner whose stored flag **claims** to be an operator and asserts the refusal, because this is exactly where a dashboard starts trusting the client.
- **Agency listing uses grouped queries, not per-agency counts in a loop** — with thirty-odd MDAs the loop is hundreds of round trips for one page, degrading exactly as the State onboards more agencies.

**The embedded web-chat widget is RETIRED**, and the way it was retired is deliberate. Customers reach this platform on WhatsApp and by phone; a third customer-facing channel was a third place for the AI to say something wrong, with its own tenant-resolution rules and its own unauthenticated model-billing endpoint. What remains:
- `/api/widget/*` answers **410 Gone** for everything, with a body naming the replacement. Not deleted, because the embed snippet is a `<script>` tag on tenants' own sites that we cannot reach in and remove — a 404 also describes an outage, a bad URL or a broken proxy, and somebody would go hunting for a fault that is not there.
- **The `/api/widget/*` CORS carve-out (`main.ts`) must stay.** Without it a tenant's browser blocks the 410 as a cross-origin violation, and the site owner sees a CORS error instead of the message explaining what happened.
- `apps/web/public/widget.js` is still served and is **inert** — it renders nothing and logs one `console.info` saying the widget was retired. An old embed leaves the page exactly as it was before the tag was added.
- `ChannelType.WEBCHAT` and existing WEBCHAT conversations/messages are **kept**. They are the record of what the business told its customers; retiring a channel is not a reason to destroy it, and the dashboard still renders those threads.
- `Organization.widgetPrimaryColor/widgetSecondaryColor/widgetPosition` still exist but are **no longer writable** — a settings form that saves and changes nothing is worse than no form. Columns kept because dropping them needs `db push --accept-data-loss`, which does not belong in this deploy path for three dead colour fields.

All of it is safe to delete once no tenant site carries the snippet. Until then these are the things telling site owners why it stopped.

**Auth**: `JwtStrategy.validate` re-checks the user in the DB on every request — deactivation and role changes take effect on the next request, not at token expiry. Do not remove this in favor of trusting token claims. JWT secrets are read from env with NO fallback anywhere (module factory throws if unset) — tests and local boots must set `JWT_SECRET`/`JWT_REFRESH_SECRET`. `tokenVersion` on User is embedded in every token and checked per request: bump it to revoke all outstanding sessions (logout/password change already do). `RolesGuard` is registered globally and reads `@Roles(...)` metadata.

**The orchestrator** (`packages/orchestrator`) is a keyword-matching intent engine, channel-agnostic, called by the WhatsApp service and the voice media-stream handler. It is the LIVE conversation engine — see the note below on the second one. Its contract: **tool intents never throw to the caller** — every DB-backed tool routes failures through `toolFailureReply()` (honest reply + `shouldHandoff: true`/`TOOL_FAILURE`), because an uncaught throw means the customer receives no reply at all. Unmatched input goes to RAG (Qdrant vector search with a Postgres ILIKE fallback) and then GPT-4o-mini synthesis with the org's persona prompt.

**TWO conversation engines exist right now, and only one is live.** This is the single most confusing thing in the repo, so read this before changing either.

| | `packages/orchestrator` | `apps/api/src/agent-tools` |
|---|---|---|
| Status | **LIVE** — serves every channel today | Built and tested, **not yet serving anyone** |
| Who runs the conversation | We do: keyword intents → RAG → GPT-4o-mini | ElevenLabs Agents does |
| Who runs the business logic | We do | We do — same services, over HTTP |
| Channels | WhatsApp, voice | Intended: WhatsApp + voice, once cut over |

Nothing has been migrated. A customer message today goes through the orchestrator, exactly as before; the agent-tools endpoints have never been called by a real agent. Do not read the ElevenLabs work as a replacement that already happened.

The split is deliberate: the agent layer replaces the CONVERSATION (turn-taking, speech, intent routing), not the BUSINESS LOGIC. Bookings, tickets, payment details and knowledge stay in the same services both paths call. That is why `agent-tools` is a thin controller over `SchedulingService`/`CrmService`/`KnowledgeService` rather than a second implementation — a second implementation would drift, and the drift would be in what customers are told about their money.

Both paths must keep the same guarantees, and they enforce them the same way:
- a tool failure never throws to the customer (`toolFailureReply()` in the orchestrator, `failed()` in `AgentToolsService`)
- payment details come only from the org's configured `payout*` fields
- a transfer is never announced before it is known to be possible
- the AI admits to being an AI when asked

Cutting a tenant over means: `POST /api/agent-provisioning/sync` (OWNER/ADMIN), point one number at the agent it created, and compare against the orchestrator path. Delete `TwilioMediaStreamHandler` and the Deepgram wiring only after a real call proves the replacement — the voice path has never completed a real call under either engine.

**Agent provisioning is generated, never hand-maintained.** `apps/api/src/agent-tools/agent-tool-catalog.ts` is the single source for the webhook tools (`TOOL_NAMES`) and the system prompt; `ElevenLabsAgentService` pushes it and records the ids, and `scripts/generate-agent-config.js` prints the same payloads as a dry run without pushing. Four things about that path are load-bearing:

- **Tools are separate resources.** `prompt.tools` is deprecated (the SDK says so outright) — each tool is created on its own and the agent holds `prompt.toolIds`. `agentDefinition()` refuses to emit both.
- **`prompt.timezone` is required.** Unset, the agent does not know what day it is, and `book-appointment` asks it to resolve "next Tuesday" into an ISO timestamp — an invented date written into a real calendar. `agentDefinition()` throws rather than defaulting.
- **The SDK is camelCase and converts to snake_case itself.** Hand-written snake_case passed to the SDK is silently dropped, taking `dynamicVariable` — the binding that stops the model supplying the caller's phone number — with it. Never bypass the SDK for these payloads.
- **The agent key is a workspace secret, not a literal header.** Tools reference it by `secretId`; our own copy is a SHA-256 hash. Rotation (`POST /api/agent-provisioning/rotate-key`) updates the secret *before* revoking the old key, so a call in progress keeps working. `scripts/mint-agent-key.js` still exists for a hand-configured agent.

`syncAgent` is idempotent, persists each tool id as it is created (so a half-finished run is resumable rather than duplicating), and refuses outright when `API_BASE_URL` is localhost or a private range — an agent that answers calls and fails every tool call is worse than none, because it looks provisioned. `getAgentStatus` is read-only on purpose: repairing drift silently also destroys the evidence of how it happened.

**Connecting a number is not symmetrical between the two channels** (`ElevenLabsNumbersService`):

- **A Twilio number CAN be imported over the API** (`POST /api/agent-provisioning/numbers/import`), because we hold the tenant's `accountSid`/`authToken` in `TelephonyConfig` and ElevenLabs takes both. **This import IS the voice cutover** — ElevenLabs answers the number from then on, not `TwilioMediaStreamHandler` — so `confirmVoiceCutover: true` is required and never defaulted, and `numbers/release` exists so the decision is reversible (releasing still leaves re-pointing the Twilio voice webhook to the operator). `enableSms` defaults to **false**, against the upstream default: this platform consumes no inbound SMS, so taking that route would change a tenant's Twilio config for nothing.
- **A SIP TRUNK CAN, and it is the only path that removes Twilio from voice** (`POST /api/agent-provisioning/numbers/import-sip`). ElevenLabs is not a carrier — `phoneNumbers.create` takes `twilio`, `exotel` or `sip_trunk`, and only the Twilio branch existed, which made Twilio a hard dependency for every call. For a State deployment a local carrier over SIP means local numbers, local termination and no overseas intermediary on citizen calls. (Exotel is India-only and deliberately not offered.) **It costs operator takeover, and that is refused rather than hidden**: the Twilio path can redirect a live call because the call IS a Twilio call, while ElevenLabs has no live-call API at all (its conversations client is get/list/delete/signed-url/webrtc-token/resolve — every one read-only or post-hoc) and `PhoneNumberTransfer` is agent CONFIGURATION carrying a prompt condition, so the agent decides, never an operator mid-call. `ElevenLabsTakeoverService` therefore refuses a SIP-trunk tenant with the reason, exactly as it does for WhatsApp, and the console shows no transfer button. The trunk itself is configured at Settings → Voice (provider `SIP_TRUNK` + `sipAddress`/`sipTransport`/`sipUsername`/`sipPassword`, the password encrypted with the other credentials); `SipTrunkProvider` in the telephony SDK refuses outbound and transfer with the real reason, because the factory's default branch used to answer `SIP_TRUNK` with a credential-less `TwilioProvider` and send the operator to check Twilio credentials a SIP tenant deliberately does not have.
- **A WhatsApp account CANNOT.** The SDK has get/list/update/delete and no create — the line is connected through the ElevenLabs dashboard via Meta's embedded signup, which needs a human. `whatsapp/attach` only assigns our agent to an already-connected line and records its id; it refuses a line whose Meta token has expired (assigning it would report success and then answer nothing).

**The live console feed is a POLLER, and there is no alternative.** ElevenLabs pushes nothing mid-conversation — every webhook event type they define (`transcript`, `audio`, `call_initiation_failure`, and the unredacted variants) fires *after* the call ends; `getSignedUrl`/`getWebrtcToken` are for a client joining as the user, not for observing. So `ElevenLabsLiveService` polls `conversations.list({agentId})` + `conversations.get(id)` every 4s and fans out over the existing `/events` Socket.IO room. Three consequences worth keeping:
- **Snapshots, not deltas.** Every emit carries the full transcript plus a turn count. With a polling source, a multi-pod fan-out and consoles that connect mid-call, a duplicate or out-of-order delta garbles the transcript while a duplicate snapshot is a visual no-op.
- **Polling is watcher-gated.** `AgentConsoleGateway` calls `watch()`/`unwatch()` on connect/disconnect; a tenant with nobody at the console generates zero provider traffic. Only decrement for a socket that actually registered — an unauthenticated socket never called `watch()`, and decrementing for it stops polling for real viewers.
- **One tenant's failure is contained.** A poll round logs and continues; an expired key for one tenant must not blank every other console. The list is scoped to the tenant's own `agentId` because the workspace may hold everyone else's conversations.

`GET /api/agent-provisioning/live` returns the same snapshot over REST so a freshly loaded console is not blank for a poll interval.

**In the console, live calls are a SEPARATE list from stored conversations** (`apps/web/src/app/agent-console/page.tsx`). A live conversation has no row in our database, cannot be replied to, and disappears when the call ends; a stored one does none of those. Merged into one list the only thing telling them apart would be a badge, and an operator would eventually type into a call that can never receive it — so selecting one clears the other, the live pane has **no input element at all** (not a disabled one), and it shows `freshness(polledAt)` rather than an unqualified "Live". Taking over needs C3; until that exists an input would be a control that silently does nothing. The agent-console socket effect must NOT depend on the selected conversation id — it used to, so every click tore the socket down and rebuilt it, which now also churns the server-side watcher count that decides whether ElevenLabs is polled at all.

**Human takeover: ElevenLabs offers NO way to stop a conversation in progress.** Their entire mutating surface is `update` on agents, tools, secrets, phone numbers and WhatsApp accounts — configuration, never a live call — and `conversations.messages` is search-only. So "tell the agent to stop responding" cannot be asked of ElevenLabs at all. `ElevenLabsTakeoverService` works around it at the carrier instead, and the two channels genuinely differ:
- **Voice is takeable.** ElevenLabs answers the Twilio number with the tenant's own credentials, so the call is a Twilio call and can be redirected out from under it — via the same `VoiceAiService.transferCallToHuman` the orchestrator path uses (`TelephonyModule` exports it for exactly this; a second "move the call" implementation is a second thing that can silently stop moving it). **Act, then announce**: the outcome is reported from what Twilio actually did, never from the intention.
- **WhatsApp is not.** The only lever is `enableMessaging` on the whole line, which silences the agent for every customer on that number. That is an outage, not a handoff, so takeover refuses it and explains why; the line-wide pause lives separately at `POST /api/agent-provisioning/whatsapp/pause` behind `confirmAffectsEveryConversation`. The console shows no transfer button for a WhatsApp thread at all.

`callSid` is deliberately not defended against being absent — all three phone-call variants in the SDK declare it required and the SDK validates responses, so a payload without one is rejected in the client first. A test pins that assumption rather than a branch pretending to handle it.

**One phone number, one contact** (`packages/database/src/phone-number.ts`). The same customer arrives as `+2348012345678` (Twilio), `2348012345678` (Meta) and `08012345678` (a staff member typing), and `Contact` is unique on `[organizationId, phoneNumber]` with exact-match lookups — so they were three different people, and a booking made over WhatsApp was invisible to the same person calling in.
- **Writes store the canonical form** (E.164 with the plus) via `normalizePhoneNumber()`.
- **Reads match every shape** via `phoneNumberVariants()` — `phoneNumber: { in: … }`. Rows written before this existed are still in their channel's format, so canonical-only lookups would leave every existing customer as unfindable as before.
- **A number the rules do not recognise is returned UNCHANGED.** Guessing at an unfamiliar shape turns one findable contact into an unfindable one, which is worse than the duplicate. The local-form rule (`0…` → `+234…`) assumes Nigeria and takes the country code as a parameter.
- The unique constraint now bites correctly: a second row for the same number is a P2002 rather than a differently-formatted string slipping through.

Existing duplicates are collapsed by `npm run contacts:dedupe` (report-only; `-- --apply` merges). Oldest row survives, a real name beats a generated placeholder, and every relation moves — conversations included, where a channel collision moves the MESSAGES into the survivor's thread rather than losing them to the `[organizationId, contactId, channel]` constraint. Deliberately a separate step: merging customer records destroys one of them, and nothing that destructive should happen as a side effect of somebody answering a phone.

**What is FREE is one search, shared** (`packages/database/src/availability.ts`). Both engines offer appointment times, and two implementations of "what is free" drift into a double booking that both paths believed was legitimate. The module imports no Prisma client on purpose — the caller passes a `BusyLoader` — because a top-level import would make the shared definition untestable in the orchestrator suites, which replace `prisma`. **Serving hours belong to the AGENCY** (`Organization.openingHour`/`closingHour`/`serviceDays`), passed in as a `ServiceHours` — a teaching hospital is not shut at weekends and a registry does not open at eight. `DEFAULT_SERVICE_HOURS` reproduces the old Mon–Fri 08:00–18:00 constants, so an agency that configures nothing is unchanged. `serviceHoursFrom(prisma, orgId)` TAKES the client for the same reason `findAvailableSlots` takes a `BusyLoader`: the orchestrator suites replace `@ace/database` wholesale, so a helper that reached for its own client was undefined in exactly the booking tests — every one of them failed with the flow silently falling back to `BOOK_APPOINTMENT`. Hours that cannot produce a slot are REJECTED at the settings endpoint and throw from the search; `serviceHoursFrom` falls back to the default instead, because it runs inside a live conversation where throwing means the citizen gets no reply. `BUSY_BOOKING_STATUSES` is shared too, so the two loaders cannot disagree about what occupies a slot.

The agent gained `check-availability` for this. Without it the agent asked the caller to name a time, tried to write it, and learned the answer from an exclusion violation — a guess-and-retry loop on a live call, while the orchestrator offered real openings on WhatsApp. The guardrail block in `agentPromptFor` instructs the agent to call it before proposing any time; that block is appended AFTER the tenant persona so a stored persona cannot override it, and `scripts/sync-payload/apply-prompt-update.js` verifies a payload carries BOTH the current `SYSTEM_PROMPT` and the current guardrails before pushing — they are separate strings, so checking only the first would let a lost guardrail through.

**What an agency offers, and where, is DATA not code** (`packages/database/src/service-catalogue.ts`). `ServiceOption` and `ServiceLocation` rows belong to one agency; the four health plans and the accredited-hospital directory that used to live in platform code are now that agency's rows, put there by `npm run catalogue:seed <slug> --apply`.

- **The catalogue is SEEDED INTO THE FLOW STATE, not queried from a slot.** `SlotDefinition.accept`/`prompt`/`skipIf`/`identifies` are synchronous, deliberately — the flow engine touches no database. So the orchestrator loads the catalogue once before the first question and seeds it under `_catalogue`, exactly as `_targets` carries the appointment list. Making the slots async to look one up would mean reworking every flow the engine runs to fix one of them.
- **`isNoCost` is a column, not a regex over the name.** Whether a citizen owes money was decided by `/equity|bhcpf|free/i` against the service LABEL, so an agency naming a paid service "Freehold Title" would have had it waived.
- **An agency with no services cannot register anyone** — the flow hands over instead of offering an empty list and refusing every answer.
- **`ServiceLocation` is unique on `[organizationId, lga, name]`, not on name.** A referral hospital serves several LGAs; keyed on name alone, one listed in four collapsed to a single row and the seed reported 46 written where 43 existed.
- **LGAs come from `state-geography.ts`, never from the locations.** An LGA where an agency has no office is still where somebody lives, and they can still register — the location slot is skipped and a human assigns one.
- **Edited at `/services`** (`apps/api/src/catalogue`, `apps/web/src/app/services/page.tsx`). Reading is open to any member — an officer on a call needs to know what the agency offers — and writing is OWNER/ADMIN, because these rows decide what the AI tells citizens. LGAs are picked from the State's list, never typed: a location filed under a misspelling exists in the dashboard and nowhere a citizen can be sent. Deleting is safe by construction — a registration stores the service and location as NAMES in contact metadata, and a half-finished form carries its own catalogue snapshot, so neither is orphaned.
- `resolveServiceOption` and `resolveLocation` return null on ambiguity rather than the first match: picking wrongly registers somebody for the wrong thing or sends them to an office that cannot help.

**Every customer-facing write goes through a FLOW** (`packages/orchestrator/src/flows.ts` and the five `*-flow.ts` files). Booking, rescheduling, cancelling, reserving and PLASCHEMA enrollment each used to be a single message in and a write out. None of them is now: each offers real options or collects real answers, and writes only what the customer chose. `FlowDefinition.summarise` is optional and the exception is narrow — booking and reserving omit the read-back because the last answer IS the decision; anything that CHANGES or DESTROYS an existing record keeps it. State lives on `Conversation.flowState`, and a flow with no thread to hang state on hands over rather than falling through to the next matching branch (VOICE has no `Conversation` row: the media-stream handler passes the callSid as the conversation id).

**Credentials at rest** — EVERY provider credential is AES-256-GCM encrypted, stored as `v1.<iv>.<tag>.<ciphertext>` with a fresh IV per write. The crypto lives in `@ace/database` (`secret-box.ts` + `credentials.ts`) rather than in the API, because the columns live there and the orchestrator package reads some of them too — a helper only the API could import would leave that path decrypting nothing.

Covered: `HostedAgentConfig.apiKey`, `TelephonyConfig.authToken/apiKey/apiSecret`, `WhatsAppConfig.accessToken/webhookVerifyToken`. NOT covered, deliberately: `accountSid`, `phoneNumberId`, `whatsappBusinessId` — those identify accounts rather than open them, and reading them in a database console is worth more than hiding them. (`CalendarIntegration` once held plaintext `accessToken`/`refreshToken` as a documented exception because nothing used the model; it has since been dropped along with `Company`, both of which had zero code references — a plaintext credential column that exists for no reason is somewhere for credentials to end up later.)

**Every read must go through `withTelephonyCredentials()` / `withWhatsAppCredentials()`, every write through `sealTelephonyCredentials()` / `sealWhatsAppCredentials()`.** A missed read does not fail loudly — it hands a `v1.…` ciphertext to Twilio or Meta, which rejects it as a bad credential, and the tenant's phone line or WhatsApp stops working with an auth error pointing at the wrong system entirely. Three rules:
- **With `ENCRYPTION_KEY` unset, writing throws** rather than falling back to plaintext with a warning — that is how a system reports encryption at rest while having none. CI sets a throwaway key for this reason.
- **A key that is not 32 bytes is rejected, not stretched.** Hashing a short passphrase into key-shaped bytes makes a weak secret look strong in every log and review.
- **Legacy plaintext still reads**, warning on every read and naming the row, so turning encryption on breaks no live phone line. `npm run secrets:encrypt` reports across all three models; `-- --apply` rewrites, and also re-encrypts anything readable only by `ENCRYPTION_KEY_PREVIOUS` (which is what makes rotation possible without every credential going dark at once). A value neither key can read is reported and **left alone**.

Masking a credential for the dashboard decrypts first (`maskStoredSecret`): masking the stored value would show the last four characters of base64 ciphertext, which changes every write and matches nothing an operator can compare against their Meta or Twilio console. The settings write paths return a masked view rather than the stored row — before encryption they echoed the tenant's own access token straight back in the response body.

**The ElevenLabs workspace has no tenancy boundary of its own**, so each tenant gets its own (`elevenlabs-workspace.ts`). Everything inside a workspace — agents, numbers, WhatsApp lines, every transcript — belongs to whoever holds the key, so a tenant with no `HostedAgentConfig.apiKey` is **refused**, not quietly dropped into the shared `ELEVENLABS_API_KEY` workspace. `ELEVENLABS_ALLOW_SHARED_WORKSPACE=1` re-enables the fallback for deployments that genuinely serve one tenant; it is deliberately not inferred from `NODE_ENV`. The in-code filtering (every listing scoped to the caller's own agent, cross-agent WhatsApp attach refused) stays as defence in depth — it is a check that has to be re-applied correctly at every listing endpoint anyone ever adds, which is why it is not the boundary.

A dedicated workspace needs **both halves**, set via `POST /api/agent-provisioning/credentials` (`{apiKey?, webhookSecret?}`): the key to act in it, and its own webhook signing secret to verify what it sends back. Setting only the key leaves a tenant whose calls work and whose transcripts are all rejected, so `GET credentials` reports `mode`, `webhookUrl` and a `warnings[]` naming exactly that gap.

**Webhook security — verify BEFORE ACK, using the raw body**:
- `main.ts` creates the app with `rawBody: true, bodyParser: false` and registers exactly one JSON parser via `app.useBodyParser('json', ...)`. **Never add another `express.json()`** — a second parser consumes the request without the rawBody hook and silently breaks every signature check.
- Meta WhatsApp: HMAC-SHA256 of rawBody (`X-Hub-Signature-256`); invalid → 403, server misconfig → 500 (so Meta retries), then ACK 200 and process async.
- Twilio: HMAC-SHA1 over callbackUrl+sorted params. Telnyx: Ed25519 over `timestamp|rawBody` (`TELNYX_PUBLIC_KEY`), 5-min replay window.
- ElevenLabs post-call: HMAC-SHA256 of `<timestamp>.<rawBody>`, header `t=…,v0=…`. Verified in `elevenlabs-signature.ts` rather than via the SDK's `constructEvent`, because that helper compares with `!==` (timing oracle) and bounds only the past, so a far-future timestamp stays replayable forever — ours uses `timingSafeEqual` and bounds both directions. **The header name is the one unverified thing**: `ElevenLabs-Signature` is documented but was never confirmed against a live delivery, so it is overridable via `ELEVENLABS_SIGNATURE_HEADER` and a delivery arriving without it logs the header names it did carry.
- **Two ElevenLabs webhook routes, one per workspace kind.** `POST /api/webhooks/elevenlabs` verifies with `ELEVENLABS_WEBHOOK_SECRET` (the shared workspace); `POST /api/webhooks/elevenlabs/:organizationId` verifies with that tenant's own stored secret and has **no env fallback** — falling back would check a tenant's transcripts against the shared workspace's secret. The org is in the path because the signature must be checked before the body is parsed, so the payload cannot be what says whose secret to use.
- **A valid signature says who SENT a delivery, never whose conversation it is.** `ElevenLabsWebhookService.ingest` takes the verified organization and refuses to attribute across it: a tenant-path delivery naming another org's agent, or a shared-secret delivery naming an agent whose org has its own workspace. Both return 200 (the sender is genuine, nothing to retry) and write nothing — refusing to attribute is not the same as rejecting.
- For all providers: when a secret/key IS configured, a missing signature header is a rejection, never a skip.

**Post-call ingestion** (`ElevenLabsWebhookService`) is how a finished ElevenLabs conversation becomes a `CallLog` or a `Conversation`+`Message` thread — tool calls show what was *done*, only this shows what was *said*. Three properties:
- **Attribution is by `agent_id` alone**, resolved against `HostedAgentConfig`. Unknown agent → dropped; two organizations claiming one agent → dropped and logged at error level. Never "the first organization" — that files a stranger's transcript and the caller's number into someone's CRM. (Enforced in code, not by a unique index: adding one to an existing table makes `db push` demand `--accept-data-loss`, and carrying that flag would silence the warning for every future schema change.)
- **Redelivery is idempotent by construction** — calls upsert on `CallLog.callSid`, and each transcript turn is inserted with a deterministic `Message.externalId` (`<conversation_id>:<index>`).
- **A conversation with no phone number and no WhatsApp id is not stored.** There is nobody to attach it to, and a placeholder contact invents a customer.

Contacts are matched across phone formats — see the phone-number note below.

**Voice calls** use TWO WebSocket layers that must not be confused: Twilio Media Streams speak a raw `ws` protocol handled by `TwilioMediaStreamHandler` (mounted via an HTTP `upgrade` interceptor in `main.ts` on `/telephony/stream/:callSid`), while the agent console uses Socket.IO gateways (`/events`, `/telephony` namespaces). `CallBroadcastService` bridges the two. In the media-stream handler, socket listeners are registered synchronously before any awaited DB work — Twilio sends `start` immediately on upgrade and a lost `start` leaves the call permanently mute.

**A voice handoff is a CALLBACK, not a transfer — by the agency's decision** (`apps/api/src/telephony/handoff-callback.ts`, shared by the Twilio and Infobip handlers). When the orchestrator returns `shouldHandoff` on a call, the AI does NOT put the caller through to anyone: it writes a `CallbackRequest` carrying the caller's own words, reads back its `CB-` reference, and an officer returns the call from the dashboard's Callbacks page. A live transfer only works while an officer is free at the exact moment a citizen asks, and fails exactly when the line is busiest; a queued callback survives that and is worked in order. So **a line needs no forwarding number**, and `voice-readiness` no longer reports a missing one as degraded — it reports the callback queue instead, flagging promises more than an hour overdue, because the thing that can actually be wrong now is a queue nobody works. Four rules hold:
- **A `CallbackRequest`, never a Ticket.** Handoff used to file a HIGH-priority Ticket, which lives on a different screen from the queue officers dial from — so "someone will call you back" was promised from a list nobody calls from.
- **One open request per citizen.** A second call from the same number reuses the open one and reads back the reference they already hold, rather than two officers ringing one person.
- **It never says the call is being put through.** The orchestrator's own reply ("Connecting you to a live human agent") is not spoken on a call, and the promise names a call, not a time — nothing here can promise "within the hour".
- **A withheld number gets no promise.** A callback queued against a number nobody can ring is a promise nobody can keep; the caller is asked to call from a number that shows.

The live transfer to a forwarding number was built for Infobip and then removed at the agency's direction. Officer TAKEOVER (`ElevenLabsTakeoverService`, an officer choosing to grab a live call from the console) is a different action and still uses `VoiceAiService.transferCallToHuman`.

**An emergency is answered before anything else, and never with a promise of rescue** (`packages/orchestrator/src/emergency.ts`, PRD §11). `detectEmergency` runs right after the handoff check, above disclosure, language, escalation and every flow — someone reporting a fire is not asked question four of a form. It matches the SHAPE of an incident ("fire outbreak", "gunmen attacked", "not breathing", Pidgin and Hausa forms), not a topic, so "fire service certificate fee" and "budget for flood control" do not trigger it; a test pins both lists. The reply gives **112** (the national number, the only one hardcoded) then `Organization.emergencyContacts` verbatim — the agency's own approved lines, set at Settings, never filled by the platform — and says an officer has been ALERTED. It never says responders were dispatched: nothing here dispatches anyone, and PlateauEYE integration is a PRD dependency, not a built one. On a call, the handoff path used to replace the orchestrator's reply wholesale, which would have swallowed the 112 guidance; both voice handlers now speak it FIRST, then the callback promise, and the callback is due now with an `EMERGENCY REPORTED` reason prefix.

**WhatsApp files are UNDERSTOOD, not placeholdered** (`apps/api/src/whatsapp/media-understanding.ts`, PRD §06). A voice note used to reach the engine as "[Customer sent a voice message]". Now: audio → Deepgram pre-recorded (same key as the phone line, language detection on); image → the configured chat model, described as citizen-supplied evidence and never as fact; PDF/DOCX → the knowledge extractor, truncated. Type, size AND magic bytes are checked before any provider sees a byte — an executable renamed `.pdf` is refused and forwarded nowhere. A file that cannot be used gets an honest "couldn't make out that voice note" and the model is never asked to guess. It runs BEFORE the takeover check so an officer holding the thread reads the transcript too.

**WhatsApp delivery is tracked on the message** (`delivery-status.ts`). Meta's sent/delivered/read/failed receipts were logged and dropped. The reply's `wamid` is now written to `Message.externalId` and receipts update `metadata.delivery`. Receipts arrive out of order, so status only moves forward (a late `delivered` cannot un-read a message); `failed` always records, with Meta's reason.

**Budget and project figures come from approved rows, never from the model** (`packages/database/src/budget.ts`, `packages/orchestrator/src/budget-answers.ts`, `apps/api/src/budget`, `/budget`; PRD §03, §04). A budget or project question is parsed deterministically (year, stage, MDA or sector, LGA), and the reply is assembled from the row's own fields and source. The LLM never sees this path. Rules, each pinned by `budget-intelligence.spec.ts`:
- **Decimal(20,2), never Float.** Summed and compared as `Prisma.Decimal`; `parseAmount` refuses `1.2e9`, `500m`, `1,00,000` and anything with more than two decimals rather than guessing.
- **Stage is never mixed.** PROPOSED / APPROVED / REVISED / RELEASED / ACTUAL_EXPENDITURE are separate rows; "how much was spent" never returns an allocation. Every allocation answer says it is not spending.
- **One document per answer, never a sum across documents.** Two approved documents that agree give the figure once (citing both); two that disagree give NO figure, hand off, and say so — `kind: 'conflict'`.
- **Only APPROVED documents answer; the uploader cannot approve** (403), and a document whose lines do not add up to its own `declaredTotal` cannot be approved by anyone. Lines change only while DRAFT; a correction is withdraw-and-reupload, audited with a reason.
- **"Budget for X" where X is in no document asks which body** rather than answering with the State total — a true figure for the wrong question.
- Returns null (unchanged behaviour) for an agency that has loaded no budget data.
- **Citizen observations about a project** ("the road was abandoned") are a `ProjectObservation`, never a change to the project's status, and are referred from the dashboard. A project cannot be published without a source.

**Socket.IO multi-pod fan-out**: `RedisSocketIoAdapter` (an `IoAdapter` subclass) must be registered in `main.ts` **before** `app.listen()` — the adapter is applied inside `createIOServer()` when Nest bootstraps the gateways. Attaching after listen does nothing (this exact bug shipped once).

**Document ingestion**: uploads go to Supabase Storage (path, not URL, stored in `storageUrl`), then a BullMQ job on Redis; `DocumentWorkerHost` runs the worker inside the API process when `REDIS_URL` is set. Extraction is mime-typed (pdf-parse / mammoth / UTF-8) — binary types must never be decoded as UTF-8 and indexed. Without Redis, only plain-text types are inline-indexed; binary uploads are honestly marked FAILED. Deleting a document must also delete its Qdrant points, or the deleted knowledge keeps answering in RAG.

**Booking integrity** is enforced by a PostgreSQL `EXCLUDE USING gist` constraint (`bookings_no_staff_overlap`, requires `btree_gist`) that lives ONLY in `packages/database/prisma/migrations/*/migration.sql` — `db push` cannot create it (Prisma cannot express EXCLUDE), so a fresh database needs every file **containing `EXCLUDE USING`** applied after push, in order (CI selects them by content, not by name, so a new one cannot be forgotten). The other files in that directory are hand-written schema changes for databases that predate them — `db push` already creates all of that, and re-running them on a fresh database collides. Application-level conflict checks are a UX nicety and a read-then-write race; the constraint is the guarantee.

**The API now refuses to start in production without it** (`config/db-readiness.ts`, called from `bootstrap()` before `listen`). Missing the migration used to be silent: the schema is complete, every query works, the dashboard loads, and the only difference is that concurrent bookings all succeed — which is how eight callers were each told they held the same slot. Outside production it warns and continues, so a developer's database can predate the migration without the check getting commented out. `ALLOW_MISSING_BOOKING_CONSTRAINT=1` is the deliberate opt-out for a deployment that takes no bookings, and it still says what has been given up on every boot.

It keys on `COALESCE("staffName", '')`, so bookings with NO staff assigned exclude against each other too. The original predicate was `staffName IS NOT NULL` — `=` never matches two NULLs, so unstaffed rows could not conflict and had to be left out — and the agent's `book-appointment` tool does not expose `staffName` at all, so **every booking a hosted agent makes was covered by nothing**. Eight simultaneous requests produced eight CONFIRMED bookings in one slot, each caller told their appointment was made. Adding a staff parameter would not have fixed it; only the database can settle a race.

**The workflow engine is real** (`workflow-executor/runner/actions/trigger` services): typed nodes (`kind`+`action`+config), durable `workflow_runs`/`workflow_run_steps`, BullMQ worker with an inline sweeper fallback, and domain events fired from CRM/WhatsApp/scheduling/telephony via `WorkflowTriggerService.emitAsync`. Runs are claimed with a conditional `updateMany` — keep it, or the worker and sweeper double-execute every step.

**Onboarding selfies** (`apps/api/src/onboarding/`): one-time upload tokens stored only as SHA-256 hashes, magic-byte image validation (SVG refused), 5-minute signed URLs, private `onboarding-selfies` bucket. This is capture, NOT verification — `verifiedAt` is never set without a real biometric provider.

**Supabase Storage requires BOTH `Authorization` and `apikey` headers** (`apps/api/src/common/object-storage.ts`) — with only the bearer token every upload fails with a misleading 400/403. Both buckets (`knowledge-documents`, `onboarding-selfies`) must be created manually as PRIVATE. Runtime `DATABASE_URL` must use the Supabase pooler in transaction mode (port 6543, `pgbouncer=true`); `DIRECT_URL` stays on 5432 for migrations.

**Appointment reminders** (`appointment-reminder.service.ts`) use an atomic claim-before-send: one raw `UPDATE ... WHERE notes NOT LIKE '%[MARKER]%'` appends the marker, and only the caller whose update count is 1 sends. This is what makes concurrent pods safe — keep claim-then-send ordering.

**Every HTTP route is accounted for, and a test enforces it** (`apps/api/test/route-accounting.spec.ts`). A route is either REACHABLE (some file under `apps/web/src` builds that path) or MACHINE-FACING (declared in the spec's registry with who calls it — the hosted agent's eleven tool webhooks, the two ElevenLabs post-call routes, the six carrier callbacks, the two probes). A new endpoint with no screen and no entry fails the test; so does an entry for a route that no longer exists. This replaces a hand audit that was run three times and gave a different answer each time (25%, then 75%, then 53, then 33), because the answer depends on noticing template-string paths, that one file can hold three `@Controller` prefixes, and that some callers are not browsers. Two rules in the matcher are load-bearing: most segments may be literal OR interpolated (the dashboard builds `/api/scheduling/${kind === 'booking' ? 'bookings' : 'reservations'}/${id}/cancel`), but the LAST literal segment must be literal — with every segment wildcarded, a brand-new `/api/mutation-probe` was reported reachable because `${API_URL}/api/${…}` appears everywhere.

**Handing a conversation to a person has ONE implementation**: `PATCH /api/conversations/:id/handoff`. `POST /api/whatsapp/conversations/:id/handoff` wrote the same three columns and was removed — they were not equivalent, because only the surviving route calls `AgentConsoleGateway.notifyHandoffChanged`, and the console called the other one. So a takeover was invisible to every other console and two officers could each believe they owned the citizen. (The agent-console carried a comment claiming the WhatsApp route was needed because it "updates assignedUserId + handoff flag", which the surviving route has always done; the difference ran the other way.) Handoff is not channel-specific — VOICE and WEBCHAT threads are handed over too.

**Writes to a citizen's record are OWNER/ADMIN/AGENT, not every member.** `SchedulingController` and `ConversationsController` had `JwtAuthGuard` alone, so a VIEWER could cancel a clinic appointment, move it, override its status, raise a refund against it, seize a live thread, or send a message as the agency. AGENT is included deliberately, unlike CRM and WhatsApp where writes are OWNER/ADMIN: this is front-desk work, and making an officer escalate to move a citizen's Tuesday slot is how agencies end up sharing an admin login. The direct status override and the refund QUEUE stay OWNER/ADMIN. `SchedulingController.getRefundRequests` used to carry the comment "(enforced by RolesGuard)" on a controller that applied no RolesGuard — a comment asserting an absent control is what a reviewer reads instead of the decorator list.

**Three packages were deleted because what they contained was invented, not written.** `packages/` is not a list of capabilities — it was carrying three workspaces that nothing imported, each one a stub that reported success it had not earned. They are gone; do not recreate them, and do not read their absence as a feature to build.

- **`@ace/voice-biometrics`** returned `verified: true, matchScore: 0.96` for any audio sample longer than ten characters, and its enrolment produced `vp_<contactId>_<Date.now()>` as the "acoustic voiceprint" with a hardcoded `confidenceScore: 0.98`. Its own suite asserted that — `assert.strictEqual(verification.verified, true)` — so the fabrication was a PASSING test. Wired to a phone line it would have authenticated every caller as whoever they claimed to be. The onboarding module already states the honest position for this platform: capture is not verification, and `verifiedAt` is never set without a real biometric provider.
- **`@ace/omnichannel-adapters`** offered Instagram, Messenger, Telegram and email, and every `sendMessage` was `return true` with no request in it — the exact shape of the shipped bug the first invariant exists for, on four channels at once. Customers reach this platform on WhatsApp and by phone; a third customer-facing channel was deliberately RETIRED (see the widget note), so four more arriving as stubs was the opposite of that decision. `ChannelType` still lists `EMAIL`/`INSTAGRAM`/`TELEGRAM`/`MESSENGER`; no code has ever written a row with one, and dropping enum values needs `db push --accept-data-loss`, so they stay — unused, not supported.
- **`@ace/scheduling-engine` kept only its iCal builder.** `generateAvailableSlots` was a SECOND answer to "what is free", which is the one thing this repo shares on purpose, and it disagreed with the real one three ways: opening hours came from a rule argument so the agency's `openingHour`/`closingHour`/`serviceDays` were ignored, it applied them with `setUTCHours` so 09:00 meant 10:00 in Lagos, and its conflict test compared only the slot's edges so a booking lying wholly inside a slot (09:50–10:00 inside 09:40–10:10) left that slot marked available. `findAvailableSlots` in `@ace/database` is the search. The package's suite now asserts `generateIcalEvent` is its only export, so the duplicate cannot come back quietly.

**An agency has SEVERAL channel lines, and the settings form must say which one it is editing.** `TelephonyConfig.organizationId` and `WhatsAppConfig.organizationId` are deliberately NOT unique: inbound calls are resolved by dialled number (`@@index([phoneNumber])`), inbound WhatsApp by Meta's `phoneNumberId` (the only tenant identifier Meta sends), `isDefault` picks the outbound line, `verifyStatusCallback` looks a row up by provider, each carrier signs its webhooks differently, and `GET /api/organizations/me` returns both as ARRAYS — `apps/api/test/telephony-inbound-signatures.spec.ts` seeds five telephony rows for one agency to exercise five signature schemes. **Do not add a unique constraint here**; it reads like a tidy-up and it deletes a capability.

What follows is that there is no such thing as "the agency's config", and both save paths assumed there was. Each did an unordered `findFirst({ where: { organizationId } })` and updated whatever came back, so on a three-line agency saving the voice form overwrote an ARBITRARY line — Twilio credentials onto the Telnyx row — and the line the officer was looking at was not necessarily the line they changed. Overwriting the wrong row's `phoneNumberId` is worse: Meta can no longer resolve that line, so every message to it logs "no config found" while the dashboard still shows it as connected.

- **The read is ordered** (`isDefault desc, createdAt asc`), because the settings screen renders `telephonyConfigs[0]`. Unordered, Postgres is free to return a different row after an UPDATE — which is exactly when an officer reloads — so the screen showed a different line each time. The order matches what `getOutboundConfig` prefers, so the line on screen is the line calls are placed from.
- **The write takes an optional `id`** — the row the screen actually rendered — and with no `id` it targets the row the read orders first, never an arbitrary one. An `id` belonging to another agency is a 404, not a fallthrough to `create`: falling through would turn an edit of someone else's line into a new line of your own.
- **The form says when there is more than one line**, naming the number it will change and stating that the others keep answering calls.

**SQL-only migrations are selected by a `-- SQL-ONLY-MIGRATION` marker**, not by grepping for `EXCLUDE USING`. The CI step's own comment had predicted the failure — "a future SQL-only constraint that is not an EXCLUDE … will not match this" — and the marker is what makes adding one a one-line change in CI, the session-start hook and the `db-readiness` remedy text instead of three.

**Dropping the two dead models is a script, not a hand-run `psql`**: `npm run models:drop-dead` (report-first; `--apply` drops; `--apply --i-have-read-the-rows` is required if any row exists). The migration file carries its precondition in a comment — verify three counts are zero, because "this migration cannot tell the difference — it drops either way" — and a precondition an operator has to remember under a `DROP TABLE` against production is the step that gets skipped at the end of a long deploy. A database created by `db push` against the current schema never had these tables, so it reports "already absent" and exits 0.

**Field names are a contract between two codebases, and a test checks it** (`apps/api/test/payload-contract.spec.ts`). It reads what every controller's `@Body()` accepts (inline types and `*Dto` classes) and what every web call sends, and fails when the dashboard sends a field the endpoint does not read — which is either a 500 from a required column left undefined, or a value silently discarded. This is the check that would have caught `{contactName, service, staff}` posted to an endpoint reading `{contactId, serviceName, staffName}`.

Three things in it are load-bearing, each learned from the spec being WRONG first:
- **It reads the whole enclosing CALL EXPRESSION**, not an adjacent `apiFetch(url, {…})`. Pages that route writes through a helper (`send(label, url, init, onDone)`) were invisible, so it compared zero scheduling mutations and reported "0 problems" — reintroducing the real bug did not make it fail.
- **`[?!]?` before the colon when reading keys.** Without it `language?: string` did not match, so every OPTIONAL field was missing from what a route "accepts" and the first run reported fourteen endpoints as discarding fields they read perfectly well. A checker that invents violations trains you to ignore it.
- **An EMPTY accepted set is a parse failure, not an endpoint that reads nothing**, and is listed as an unchecked gap rather than compared against.

An interpolated segment on the caller's side may stand for a literal on the route's side (one call expression serves both `bookings` and `reservations`), so the accepted set is the union of every route it could reach.

**A citizen can phone the agency from inside WhatsApp, and that path has TWO halves with very different maturity.** Calling is switched on per line from Settings → WhatsApp (`setWhatsAppCalling`, which reads Meta's verdict back rather than trusting its own 200), and Meta then delivers call activity on the `calls` webhook field.

- **The `calls` field has to be SUBSCRIBED or none of this runs.** `subscribeWhatsAppWebhooks` asks for `messages,calls` together and, on a refusal, retries `messages` alone and reports the gap as its own failed step — the `calls` permission is not granted to every app, and one request carrying both names would have had the working messaging subscription refused along with it.
- **Recording is live** (`WhatsappService.processCallEvent`). A call event used to fall into the `!message` branch and be dropped at debug level, so a citizen who needed help got nothing and nothing recorded it. It now resolves the tenant by exact `phoneNumberId`, writes a `CallLog` keyed on Meta's own call id (only a `terminate` writes the outcome, so a redelivered `connect` cannot put a finished call back to RINGING), stores numbers canonically because Meta sends a wa_id with no plus, and uses `provider: WHATSAPP_CLOUD` — absent from `TELEPHONY_PROVIDERS` so it cannot be chosen as a carrier, because recording a Meta call as a Twilio one sends whoever investigates it to the wrong console.
- **ANSWERING is built, OFF by default, and has never carried a real call** (`whatsapp-call-answer.service.ts`). Meta sends an SDP offer and expects an SDP answer POSTed to `/{phone-number-id}/calls`; there is no `<Connect><Stream/>` equivalent, so the API has to terminate WebRTC itself — ICE, DTLS, SRTP, Opus — via `werift`. Four things about it are load-bearing:
  - **It refuses to enable on the flag alone.** `WHATSAPP_CALL_ANSWER=1` *and* a TURN relay (`TURN_URL`/`TURN_USERNAME`/`TURN_CREDENTIAL`) are both required, and `readiness()` reports a missing relay as BLOCKED. WebRTC media is UDP and a Render web service exposes one HTTP port with no inbound UDP, so media must relay through TURN. Answering without one is **worse than not answering**: the call is consumed, the carrier reports it completed, and the message fallback never runs.
  - **It requires a `typ relay` candidate, not merely a candidate.** A `host` candidate is always gathered and is always useless — it is the pod's private address. The first version of that check matched `\S+ typ relay`, which matches nothing, because `typ` sits seven fields into an ICE candidate line: it would have declined every call even with a healthy relay, and that decline is indistinguishable from broken TURN. A test pinning a real relay candidate is what caught it.
  - **Every refusal falls back to the message path**, and the thread note distinguishes "not configured" from "tried and failed: <reason>" so staff can tell which. `blocked` on the outcome is what carries that distinction.
  - **`negotiate()` is a protected seam** so the tests can reach the branches after negotiation. A sandbox cannot allocate a relay, so without it the only reachable outcome would be "no relay" and Meta's refusals would be untested.
  - **The media bridge exists** (`whatsapp-call-media.service.ts`): Opus in → Deepgram → orchestrator → ElevenLabs → Opus out, the same chain `TwilioMediaStreamHandler` runs over a simpler transport. Four decisions in it are load-bearing.
    - **Opus is DECODED, not forwarded.** Twilio's mulaw/8000 goes to Deepgram untranscoded; the equivalent shortcut here would be `encoding=opus`. Deepgram documents raw opus for its **Flux** model and the general encoding list includes opus, but it is NOT established for the `nova-2` streaming model this platform uses — and being wrong means a caller who is never transcribed, which is indistinguishable from a caller who said nothing. `opusscript` decodes to linear16 instead; it is pure JavaScript, chosen over `@discordjs/opus` because the Render build has no toolchain to fall back on if a prebuilt binary is missing.
    - **`createDeepgramWsForOrg` takes the wire format**, defaulting to mulaw/8000 so every Twilio caller is unchanged. Telling Deepgram mulaw while sending 48 kHz PCM transcribes every word at the wrong speed and pitch — nonsense, not an error — so a test pins the parameters.
    - **TTS is fetched as `pcm_24000` and upsampled by exactly two.** ElevenLabs offers no `pcm_48000`, so a resample is unavoidable; 24→48 is an integer factor with no fractional accumulator and no drift, where 44.1→48 is 160/147 and needs a real resampler whose errors are heard as a robotic voice. Interpolated, not sample-doubled, because doubling mirrors the spectrum around 12 kHz.
    - **The RTP payload type comes from what Meta NEGOTIATED**, not the 111 everyone assumes, and the timestamp advances a whole 960-sample frame per packet. Either one wrong is silently discarded or stuttered at the far end with every byte otherwise correct, so both are asserted.
  - **Still unproven end to end.** The codec round trip, the arithmetic, the framing and the whole chain are tested against the real libraries with the far ends faked, but a sandbox allocates no relay and places no call, so no packet has crossed the transport. Do not read "the service exists" as "WhatsApp calls work" — the same warning `TwilioMediaStreamHandler` carries, and its protocol is far simpler.

**Outbound webhook events are ONE list, in `@ace/shared-types`, and a test checks it** (`WEBHOOK_EVENTS`, `apps/api/test/webhook-events.spec.ts`). The dispatcher and the white-label screen each carried their own copy, and they had drifted three ways at once: the screen offered `call.ended` while the API dispatched `call.completed`, so a tenant ticked Call Ended, saw it saved and never received one — `WebhookDispatcherService` filtered on an exact string match, so the dispatch returned at the filter with nothing failing and nothing logged, which looks exactly like an event that has not happened yet. `contact.created` was dispatched and offered nowhere, leaving it receivable only by a tenant holding `'*'`, which no screen can set. `appointment.booked` and `handover.requested` were offered and dispatched by nothing at all.

- **Subscriptions are matched on CANONICAL names, both directions** (`isWebhookEventEnabled`). The write path for `enabledWebhookEvents` validates nothing, so a row can hold any string a tenant ever sent — renaming the dispatch alone would have silently unsubscribed everyone holding the old name, the same bug from the other end. `call.completed` is an alias of `call.ended` and both keep working. `'*'` still means everything.
- **`delivered: false` is what stops the screen offering a subscription that cannot fire**, and it is not a placeholder for the UI to fill in. An operator who ticks an event and waits has no way to tell "never happened" from "never implemented". Nothing carries the flag today; it exists for the next event added ahead of its dispatch.
- **`appointment.booked` and `handover.requested` go out through a HELPER, not a bare `dispatch`** (`WebhookDispatcherService.appointmentBooked` / `.handoverRequested`), because each has several firing sites and a hand-built payload at each would drift. Callers pass an id; the payload is built once, from the row.
  - **Both booking WRITERS dispatch, not just the service.** `SchedulingService.createBooking` serves the dashboard and the hosted agent, while the orchestrator writes its own `prisma.booking.create` — so the WhatsApp service and the voice media-stream handler dispatch from the orchestrator's result, read through `bookedAppointmentId()` in `@ace/shared-types` so the two channels cannot disagree about what counts as booked. Dispatching only from the service would have fired for staff bookings and silently not for the channel serving every citizen.
  - **A handover fires on the false→true TRANSITION, from all five writes that activate one**: an officer replying (one site per channel), the toggle route, the orchestrator returning `shouldHandoff`, and the `SET_HANDOFF` workflow action. The state is not the event — every one of those writes sets the flag whether or not it was already set, so dispatching on the write delivers a webhook on an officer's every message to a thread they already hold. Releasing a handoff is deliberately not an event: nothing was requested, and the catalogue has no name for it. **VOICE dispatches no handover at all** — that handoff redirects the live call at the carrier and there is no `Conversation` row to name.
  - Two tests guard it. `webhook-events.spec.ts` would otherwise have been satisfied by the dispatcher dispatching to ITSELF — the helper's `dispatch(...)` lives in `webhooks/`, so the scan found both events with no domain code calling anything — and it now also requires each helper to have callers outside `webhooks/`, names the paths that must be among them, and fails when a file that activates a handoff does not dispatch. That last check first reported `analytics.service.ts` and `platform.service.ts`, which read the flag in a `where` clause to COUNT handed-over threads: it now decides write-versus-read by the nearest preceding `data:`/`where:`/`emit(`, and a companion test asserts the real writers are still recognised so the check cannot pass by matching nothing. `webhook-domain-events.spec.ts` drives the real routes, because a missing `WebhooksModule` import is a runtime DI failure no source scan can see.
- **The spec scans `apps/api/src` for the dispatch literals** and fails on an event with no catalogue entry, an entry claiming delivery that nothing dispatches, a `delivered: false` that something does dispatch, and an ALIAS being dispatched (aliases exist for stored subscriptions; sending one restarts the drift). It also asserts the scan found something — a scan matching nothing would pass every other assertion against an API dispatching no webhooks at all.
- **The toggle writes the canonical key and drops its aliases**, and converts a `'*'` row to the explicit set on first use. `'*'` cannot express "everything except this one", so without that the switch read as on, removed nothing and changed no subscription.

**Whether a call can actually complete is reported, at `GET /api/telephony/voice-readiness` and on the telephony screen.** Four separate misconfigurations each produce a call that CONNECTS and goes nowhere, and Twilio reports every one of them as answered and completed — so a failed test call looked identical to a wrong number, and nothing anywhere said which:

- **No `ELEVENLABS_API_KEY` and the caller hears PURE SILENCE.** The inbound TwiML for Twilio is `<Connect><Stream/>` and nothing else — `generateInboundWebhookResponse` takes a `promptText` and discards it — so the greeting is spoken by the media-stream handler over the socket. No TTS, no greeting, no anything.
- **No `DEEPGRAM_API_KEY` and the caller is never transcribed.** They hear the greeting, speak, and nothing answers.
- **A wrong `API_BASE_URL` refuses every call.** The Twilio signature is computed over `API_BASE_URL + the route path`, so a mismatch — http for https, a trailing slash, the web app's host instead of the API's — answers "This call could not be authenticated", which reads as a bad auth token and sends the operator to check the wrong thing. The report prints the webhook URL **from that same expression**, so what it shows is what will be verified against.
- `/api/health` is liveness and touches nothing; `/api/health/ready` covers PostgreSQL and Redis. Neither knows anything about voice.

It is OWNER/ADMIN, returns no credential value (the stored token as a length plus its last four characters, which is what an operator compares against the Twilio console; env keys as present or absent), and separates **blocked** from **degraded** — a missing forwarding number is reduced service, not a broken line, and conflating the two buries the real blocker among warnings. `forwardingNumber` is reported PER LINE because it lives on `TelephonyConfig`, not on the organization.

**The telephony screen's carrier panel was two editable inputs with no save path**, pre-filled with `+234 1 700 8000` and `+234 803 123 4567 (MTN Business Line)` — and the forwarding one was never assigned from the API at all. So an unconfigured agency was shown a phone number and an MTN business line that belonged to nobody, as its own configuration, on the screen an operator uses to check whether their line works; and typing a real forwarding number into it sent nothing anywhere. It is read-only now and names every line the agency holds. **`customer-journeys.spec.ts` J2 asserted the removed "Start Demo Simulation" button was VISIBLE** — the suite was pinning the fabricated simulator in place, so deleting the fabrication is what made the test fail. It now asserts the button is absent.

**A test app is not the real app unless it is configured like one** (`apps/api/test/support/create-test-app.ts`). `createNestApplication()` does NOT run `bootstrap()`, so nothing `main.ts` installs is present unless the suite installs it too — and exactly one of fifty-two did. The other fifty-one ran with **no global `ValidationPipe`**, which means no suite but that one could prove any route's DTO validation holds: a `@MinLength(8)` on a password could be deleted and every one of them would still pass. It also manufactures findings — a deliberately invalid body comes back 201 instead of 400, and the honest reading of that is "validation is missing in production", which it is not. A harness that invents security findings is worse than one that misses them, because the next real one gets dismissed as another artefact. `rawBody` belongs there for the same reason: every carrier signature is verified against the raw buffer.

**An invited officer must be invited at an address they can sign in with.** `AuthService` looks a user up with `email.trim().toLowerCase()` everywhere — login, forgot-password, resend-verification — and `register` lowercases before writing. `addTeamMember` wrote `userData.email` exactly as the administrator typed it. So an invite to "Jane.Doe@Plateau.gov.ng" stored a row no lookup could ever find:

- the invite link still worked, because `setupAccount` matches on the TOKEN, so she set a password and was signed straight in and everything looked correct;
- next time she signed in, `findUnique({ email: lowercased })` found nothing and she was told "Invalid email or password credentials";
- forgot-password lowercases too, so it found nothing and returned its deliberately vague "if an account exists" message while sending nothing. The account did exist.

She was locked out permanently with no route back through the product and nothing in any log saying why. `User.email` is `@unique`, so this also allowed "Jane@x" and "jane@x" as two different officers. The address is normalised at the one place that writes it, and a clash is a stated refusal rather than a P2002.

**`POST /api/auth/refresh` keeps its own refusal reasons.** The handler wrapped everything in `catch { throw new UnauthorizedException('Invalid or expired refresh token') }`, swallowing the specific exceptions it had just raised — so a deactivated officer and a signed-out session both came back as a generic token error, which reads as a client bug. There is nothing to protect: whoever presents a validly signed refresh token already holds that account's credential, and a login attempt states the reason plainly anyway.

**A console socket is re-checked for as long as it is open** (`apps/api/src/events/socket-auth.ts`). `authenticateSocket` ran in `handleConnection` and nowhere else, and a socket stays open as long as the tab does — hours — streaming every customer message, call transcript and handoff event for that tenant. Nothing revisited the decision, so four controls the product reports as immediate were not:

- **Deactivating an officer** cut HTTP on the next request and left their open console receiving everything. The comment on `authenticateSocket` claimed precisely this was prevented.
- **Logging out** or changing a password bumps `tokenVersion`, which kills every issued token — and did nothing to the socket already holding one.
- **Suspending an agency** refused every member's next request while their consoles kept streaming; suspension was not checked on the socket path at all, not even at connect.
- **The access token expiring** bounded HTTP access only.

`socketRevalidator` sweeps every connected socket once a minute, re-running the same checks, and disconnects with a REASON the console can show — a silent drop reads as a network fault, so the officer reconnects and wonders why it keeps happening. One implementation shared by both gateways (`AgentConsoleGateway`, `VoiceStreamGateway`); a second copy is a second thing that can silently stop revoking. It is a module singleton rather than a Nest provider because the gateways live in different modules and exporting one between them reintroduces the cycle `TelephonyModule` already works around. A database blip does NOT disconnect everyone: a failed check is skipped and retried on the next sweep, since a socket is no more privileged for having survived one. Platform operators stay connected through a suspension, the same exemption `JwtStrategy` makes.

**Every route back into a staff account is EMAIL, and email is optional.** `RESEND_API_KEY` is declared optional in `env.validation.ts` — correctly, because citizens are served on WhatsApp and by phone and need no email provider at all — but the staff invitation, email verification, resend-verification and the password reset all depend on it, and each one answered 200 with nothing delivered. The invitation is the worst: an invited officer is created with a bcrypt hash of random bytes so no password reaches the account, and the invite token is stored only as a SHA-256 hash, so once `addTeamMember` returns the raw link exists NOWHERE. An administrator was told the officer was invited, the officer got nothing, and the link needed to repair it was already gone — with no way out inside the product, because every other way in is also an email.

- **`Resend.emails.send()` RESOLVES with `{ data, error }` and does not throw on an API error.** A `try/catch` around it catches a network fault and nothing else: an invalid key, an unverified sending domain, a suppressed address and a rate limit all came back as success. `sendEmail` returned `true` for refused mail, which defeats the entire point of its returning a boolean. Both call sites read `result.error` now.
- **`addTeamMember` reports delivery** (`emailDelivered`, `deliveryProblem`) and, when it FAILED, returns `inviteUrl` to the administrator who just created the account. That is not a widening of access — they are OWNER/ADMIN, they created the user a moment ago in their own agency, and they can delete and re-invite at will. An officer who can never sign in is far worse. It is never returned on success.
- **`forgot-password` no longer says instructions "have been sent."** What must stay vague is whether the ACCOUNT exists — identical wording for a known and an unknown address is the anti-enumeration property. Whether the MAIL SYSTEM works is not a fact about the account, so the response says what to do when nothing arrives, and the failure logs at ERROR level in every environment rather than a `NODE_ENV`-gated `[DEV]` line.
- **`npm run user:password` is the break-glass path** (report-first; `-- <email> --apply` sets a generated one; `--stdin` takes it from standard input so it stays out of argv and the shell history). With no argument it LISTS every account with the flags that decide whether it can sign in — deactivated, unverified, locked out, invite still pending — which is the question an operator actually has. Bounded by who holds database credentials, exactly like `npm run platform:grant`. Setting a password this way bumps `tokenVersion`, spends any outstanding invite or reset token, and clears a lockout.

**"Configured" is not an answer, so the platform ASKS each provider** (`apps/api/src/diagnostics/provider-health.service.ts`, `GET /api/diagnostics/providers`). Every readiness surface here reported a provider as working because its environment variable was non-empty — `voice-readiness` said "Text to speech (ElevenLabs): configured" on the strength of `!!process.env.ELEVENLABS_API_KEY`. A key that is revoked, mistyped, out of credit or belonging to a different account is indistinguishable from a working one: every screen is green, and the first thing that discovers the truth is a citizen on the phone hearing silence. **That exact failure had already happened on the carrier** — the deployment held a valid Twilio SID and token beside a phone number from a different account, and the voice report said "A call will connect and be answered" when no call could ever arrive.

One cheap read-only request per provider — list projects, fetch models, name the authenticated user — never one that sends a message, places a call or spends credit. Three states, and the middle one is the point: `ok` (it accepted the credential), `failed` (it answered and REFUSED, quoted verbatim, or could not be reached — "check your configuration" is what somebody reads instead of the actual cause), `not_configured` (no credential, which is not a fault on its own, so what its absence COSTS is stated). Checks: Deepgram, ElevenLabs (**the tenant's own workspace key when it has one** — proving the shared key proves nothing about that tenant's calls), OpenAI, Qdrant, Supabase Storage, Resend, and Meta WhatsApp **per line with that line's own stored token**, since an expired Meta token is the usual cause of a line the dashboard shows as connected that answers nobody. A PUBLIC `onboarding-selfies` bucket is a FAILURE — citizens' faces on an open URL — reported and deliberately not changed, because objects are already in it. No credential value or ciphertext ever appears in the response, and a test asserts that.

**`voice-readiness` asks the carrier too, for the same reason.** Every check in it described what THIS PLATFORM holds; none could see whether Twilio has the number and where it sends the calls. It now asks, per line: `blocked` when the account does not hold the number or its Voice webhook points elsewhere (a new Twilio number points at a demo greeting, so the caller hears that instead), `degraded` when Twilio could not be asked — unknown stays unknown, because treating "could not check" as "works" is exactly how this got it wrong — and `ready` only when Twilio itself confirms.

**`POST /api/telephony/adopt-deployment-line`** exists because a deployment can hold `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN` and `TWILIO_PHONE_NUMBER` and still answer every caller "This number is not currently configured": nothing ever wrote them into a `TelephonyConfig`, and tenant resolution matches the dialled number against that table FIRST, so the call is over before any credential is read. Four guards — all three variables present, the agency has no line, the deployment serves exactly ONE agency (a count, no identities), and `confirmAdoptsDeploymentNumber`, because this decides which agency answers the State's phone number.

**`POST /api/telephony/point-number-at-platform`** is the last step that was manual only because nothing had been written to do it. `pointedHere` is true **only when Twilio echoes back the URL we asked for**; a 200 carrying a different `voice_url` reports NOT pointed here, because reporting the request as the outcome is the fabrication the act-then-announce rule exists to prevent. When the number is not on the account it lists what that account DOES hold — "not on this account" is true and a dead end, and the credentials have just answered, so the refusal can be the answer instead.

## Non-negotiable invariants (each reverses a shipped bug)

1. **Never fabricate success or data shown to humans**: no invented bank accounts/USSD codes, no fake call records when a provider API fails (throw with the reason), no placeholder quotes/prices, no "PAID" status on unpaid bookings, no links to endpoints that don't exist. Degrade honestly and hand off to a human. **This covers BUTTONS, not just data.** The scheduling screen's "Cancel Booking", "Reschedule Slot", "Cancel Reservation" and "Mark Completed" each showed *"Booking for Jane Citizen cancelled."* and made no request at all — the citizen's appointment untouched, the officer told it was cancelled. Seven endpoints existed for those actions and the page called none of them. A test asserting the confirmation message would have passed against it, which is how it survived: `apps/web/e2e/scheduling-actions.spec.ts` asserts on the REQUEST. The same screen also invented two tags (`contact.tags || ['customer', 'active-lead']`) for a citizen who had none, and offered a knowledge "download" for crawled pages whose `storageUrl` is a web address rather than a bucket path — signing that produced a URL to an object that does not exist.
   **And it covers a mutation whose failure is discarded.** Deleting a knowledge document removed the row from the list whatever the response was, so a refused delete (OWNER/ADMIN) looked identical to a successful one while the document stayed indexed and kept answering citizens. Three CRM state changes and a selfie-request cancel fired and ignored the result, so a refusal showed nothing at all. And a failed LIST load rendered the empty state — *"No bookings recorded yet. Click Create Booking above to add one."* — which is a statement about the agency's diary made when nothing is known about it, and it invites an officer to create a booking that already exists.
2. The AI must identify as an AI when asked (regulatory + Meta policy). Do not restore any "I'm a human" persona reply.
3. Payment details shown to customers come ONLY from the org's configured `payoutBankName/payoutAccountName/payoutAccountNumber/payoutUssdCode` fields; unset → defer to a human.
4. Env naming drift: telephony historically read `API_URL` while the rest reads `API_BASE_URL`; code now falls back between them — preserve the fallback if touching those paths.
5. Conversation lists must return the LAST N messages (query desc, reverse for display), never the first N.

## Deploy notes

Deployment configs: `render.yaml`, `Dockerfile.api`, `Dockerfile.web`, `kubernetes/deployment.yaml`. After any `schema.prisma` change, `npm run db:push` must run against the production DB **before** the new code deploys — Prisma selects all mapped columns, so new columns missing in the DB break unrelated queries. Startup env validation (`env.validation.ts`) hard-fails the boot on missing required vars and warns on optional ones; add new env vars there.

**The dashboard distinguishes UNKNOWN from ZERO, and that is the whole design of `AnalyticsService`.** Every query in it was wrapped in `.catch(() => 0)` inside a try that logged and carried on, so a database one connection short of the pool limit returned HTTP 200 with a complete set of zeros — "0 citizens", "0 open tickets", "₦0" — presented to an officer as the state of their agency. The home page could not have told the difference: every fetch behind it ends in `.catch(() => null)` with an 8-second abort, and it had no error state at all.

- **A figure that could not be read is `null`, and `unavailable[]` names it.** One broken count does not blank the screen; the rest still renders, those cells show `—`, and a banner lists what is missing. A rate whose numerator or denominator is unknown is `null`, not `0%`.
- **Days are bucketed in `Organization.timezone`** (`apps/api/src/common/zoned-days.ts`), not the server's. Render runs UTC, the default is Africa/Lagos, so a conversation at 00:30 in Jos was counted on the previous day — and the window was `Date.now() - days * 86400000`, which started at whatever time of day the page happened to be opened, so two officers refreshing an hour apart saw different numbers for days that had already ended. One `zonedWindow()` call produces both the window and the buckets, so they cannot disagree.
- **The three chart series are three series.** The payload carried one undifferentiated conversation count, which the page drew under a "WhatsApp" legend with WebChat hardcoded to zero — a WEBCHAT thread was displayed as a WhatsApp message. Voice is counted from `CallLog` on purpose: a call creates no `Conversation` row, so a conversation count reports every phone call as zero.
- **`pipelineValue` is open pipeline, and the card says so.** It was labelled "Premiums Collected — Informal sector & contributions" over the sum of every `Deal.amount` at any stage, on a platform that collects no payments: naira the State had not taken, on the first screen anyone sees. It is also summed in the database now; `findMany()` over every deal ever recorded, to add one column up in JavaScript, grows without limit.
